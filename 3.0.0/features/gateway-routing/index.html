    Trino Gateway Routing

    A Trino Gateway cluster installed by chango starts with no routes. Installing it puts the process on a host; it does not tell it which Trino clusters exist or who may reach them. Until the routing topology is registered, every query through the gateway fails — typically with a 401, which reads like an authentication problem and is not one.

    This is the step most often missed after an install, so it is worth being explicit about what has to exist and where each piece lives.

    Who owns what

    The topology is split across two products, and that split is the thing to understand first.

    Owned by Managed through
    Clusters — where a Trino coordinator is chango /admin/api/gateway/clusters
    Cluster groups — which clusters a group of users may route to chango /admin/api/gateway/cluster-groups
    Resource groups — query concurrency and memory limits chango /admin/api/gateway/resource-groups
    User → group membership Ontul The Ontul admin UI

    chango master is the authoritative store for the first three. It persists them through the replicated metadata store (KMS-encrypted, leader-written, synced to followers) and the stateless gateway instances pull the assembled topology from GET /api/v1/gateway/topology.

    Membership is different. It used to live in chango and no longer does:

    User-group membership moved to Ontul

    POST and DELETE on /admin/api/gateway/user-groups answer 410 Gone:

    user-group assignment moved to ontul IAM — manage groups + membership
via the ontul admin UI; chango mirrors them automatically

    Create the group in chango (cluster-groups), then add users to the matching Ontul group in the Ontul admin UI. chango mirrors the membership.

    GET /admin/api/gateway/user-groups still works and is the quickest way to see the mirrored result.

    Creating a cluster-group in chango creates the corresponding Ontul group as a side effect, so the name is shared. Adding people to it is Ontul's job.

    The gateway asks Ontul too — and that token is filled in for you

    Every initial query is authorized by the gateway itself, against Ontul, under its own service identity (Token <value> on /v1/api/authz/check-batch). chango resolves that token from the running Ontul cluster at install time; there is nothing to paste.

    When it is missing the failure is misdirected. Routing still works, so SELECT 1 and SHOW CATALOGS pass, and only queries that touch a table fail:

    403  {"error":"authorization unavailable: ontul authz returned HTTP 401: …"}

    That message reads as an Ontul outage, which sends you to check policies and group membership — neither of which is wrong. Confirm the property instead:

    curl -s "http://master:8080/admin/api/trino-gateway/<id>/config"   -H "Authorization: Bearer $TOKEN" | python3 -c   'import json,sys;[print(l) for l in json.load(sys.stdin)["properties"] if "authz" in l]'
#   gateway.ontul.authz.url=http://…:18080
#   gateway.ontul.authz.token=OTOK…        ← empty means this failure

    Rotating the service identity afterwards is a config edit — Configure → IAM Service Token** in the console, or ontulAuthzToken on POST /trino-gateway/<id>/config. Supplying one at install time overrides the auto-discovery, for deployments that mint a dedicated service principal.

    Minimum viable topology

    Three things, in this order.

    1. Confirm the routing target

    A Trino cluster installed by chango registers itself — the coordinator URL is something chango already knows, so it is not worth retyping. Check it:

    BASE=http://<master>:8080
TOK=$(curl -s -X POST $BASE/admin/api/auth/login \
      -H 'Content-Type: application/json' \
      -d '{"username":"admin","password":"…"}' | jq -r .accessToken)

curl -sS $BASE/admin/api/gateway/clusters -H "Authorization: Bearer $TOK"
#   [{"clusterName":"trino-main","clusterType":"trino",
#     "url":"http://<coordinator-host>:<httpPort>","activated":true}]

    Register by hand only when the entry is absent — an external Trino cluster chango did not install, or a cluster installed before the gateway existed. The admin UI has the same thing under the gateway page's Routing Targets.

    curl -sS -X POST $BASE/admin/api/gateway/clusters \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{
    "clusterName": "trino-main",
    "url": "http://<coordinator-host>:<httpPort>",
    "activated": true
  }'

    Registration is not membership

    A registered cluster routes nothing until a cluster-group lists it (step 2). chango never creates or widens a group — not even default. Several Trino clusters can sit behind one gateway, so a new cluster quietly joining the group admin routes to would scatter operator queries across clusters sized for different work.

    activated is the operator's drain switch

    Turn it off and new queries go to the group's other clusters while running ones finish — that is how a backend is replaced without a maintenance window. chango writes this field once, at registration, and never again, so a cluster you drained stays drained. The one thing it keeps following is url, for when a coordinator moves; deleting the Trino cluster removes the entry.

    2. Create a cluster group

    Every route needs at least one. Routing is owned by groups, not by raw host:port backends — a gateway with a registered cluster but no group still has nowhere to send a query.

    curl -sS -X POST $BASE/admin/api/gateway/cluster-groups \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{
    "groupName": "default",
    "trinoClusterIds": ["trino-main"]
  }'

    trinoClusterIds holds the names registered in step 1.

    3. Add users to the group — in Ontul

    Creating a cluster-group also creates an Ontul group of the same name (chango writes to Ontul first and aborts if that fails, so the two cannot drift). Open the Ontul admin UI, find that group, and add the users who should route through it. A user in no group has no route.

    Confirm the mirror landed:

    curl -sS $BASE/admin/api/gateway/user-groups -H "Authorization: Bearer $TOK"
#   {"admin":["admin-group"],"analyst":["analyst-group"]}

    The group is created empty — membership is not permission

    A group with no policy attached routes fine and then denies every table. SELECT 1 succeeds, SELECT … FROM <table> is a 403. Routing and authorization are separate axes: the cluster-group decides which engine, the policy decides what is visible.

    default is the group admin routes to and is deliberately left empty — the operator's own access comes from admin-group's AdministratorAccess. Put users in purpose-built groups instead, so that separating a user-facing engine later does not move the operator path with it.

    How a backend is chosen

    A cluster group can hold more than one engine. The gateway picks one per user, by Highest Random Weight over the group's activated members — not per request.

    The reason is narrow and worth stating, because it decides what a deployment can do with a load balancer. Session properties, USE, and prepared statements all live client-side: the client resends them on every request, so any engine can serve any of them. An explicit transaction does not — it lives in the coordinator's memory, and the client only echoes its id back in X-Trino-Transaction-Id. Choosing per request meant the statement after START TRANSACTION could land on an engine that has never heard of that id. With two engines in a group the next statement stayed put half the time, so the failure was intermittent — the kind that gets written off as a network problem.

    HRW rather than hash(user) % n because the candidate set changes: draining or adding an engine reshuffles nearly everyone under modulo, while HRW moves only the users whose top choice left. It cannot be zero — a user whose own engine is drained mid-transaction loses it, and no routing scheme prevents that.

    It is deterministic, so every gateway instance reaches the same answer from the same topology snapshot, with no shared state.

    Two users are not a distribution test

    HRW allows two users to land on the same engine, and eight users all landing on one of two engines happens about once in 128. To see the spread, use many users and check that both engines are reached; to see stability, query repeatedly as one user and check the coordinator never changes.

    The gateway holds no query state

    The chosen backend travels inside the response URLs, encrypted (AES-GCM) under a secret that is identical on every gateway of the cluster. So any instance can serve any poll of any query.

    That has a practical consequence: nothing about the gateway requires sticky sessions. chango's generated nginx uses ip_hash, but only because one rule covers every component surface and some components genuinely need it (the catalog server's OAuth, the IAM engine's JWT). A deployment is free to front the gateway with round-robin or a cloud load balancer.

    Verified by starting a query on one gateway and polling it to completion on the other.

    Client tags

    The gateway adds cg=<cluster group> so the backend's resource-group selector can route the query to that group's queue. Tags the client sent are kept — a cost centre, a dashboard id, an application name all arrive intact, so resource-group rules and audit queries that select on them keep working. Only the cg= namespace is the gateway's, and a client value there is replaced: otherwise a client could put itself in another group's queue.

    client sends: team-x,cost=1234      coordinator sees: team-x, cost=1234, cg=analyst-group
client sends: cg=default,mine       coordinator sees: mine, cg=analyst-group

    Draining

    Setting activated: false on a routing target takes it out of the candidate set. The users whose top choice it was move to another engine in their group; everyone else stays where they were. Re-activating restores the original placement.

    A write to the routing registry replaces the whole entry

    There is no partial update. Sending just {"clusterName":"trino-2","activated":false} to drain would drop the url, and a routing target without one fails every query routed to it. That is now refused with url is required, but the correct move is to read the entry, change the one field, and send the whole document back.

    The client surface — nginx, and it is always TLS

    Clients do not talk to a gateway instance. They talk to an nginx surface in front of the gateways, and chango does not create it at install — apply it after the cluster is up.

    curl -sS $BASE/admin/api/trino-gateway/<clusterId>/nginx -H "Authorization: Bearer $TOK"
#   gateways[] / nodeManagers[](nginxInstalled) / recommendedNode

curl -sS -X POST $BASE/admin/api/trino-gateway/<clusterId>/nginx \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"nodeId":"<nm nodeId>","listenPort":0,
       "gatewayInstanceIds":["tg-1-gateway-1","tg-1-gateway-2"]}'
#   nginxPort     19300
#   nginxApplied  host-a:8680,host-b:8680     ← should list every gateway

    An empty gatewayInstanceIds means remove the proxy, which is what the console's Remove Proxy sends. Two requests that would have been read that way by mistake are refused with 400 instead:

    • gatewayInstanceIds empty (or missing — a misspelled field such as endpoints is dropped) while no proxy is applied: gatewayInstanceIds is empty and no proxy is applied, so there is nothing to apply and nothing to remove …, followed by the gateway instance ids of this cluster;
    • ids were sent but none of them is a gateway instance of this cluster: none of the requested gateway instances were recognised: [...], with the same list.

    Both used to answer 200 with the cluster JSON and leave conf.d empty — the gateway then had no TLS front, and since Trino's JDBC driver refuses Basic credentials over plain HTTP, nothing authenticated could reach it.

    listenPort: 0 auto-allocates from a dedicated band. A port given explicitly is honoured only after it is confirmed free — nginx binding silently fails otherwise, which leaves a surface that reports success and refuses connections.

    TLS is not a choice here: Trino's JDBC driver refuses to send Basic credentials over plain HTTP, so a plaintext surface cannot be used by the clients that matter, and any tool that does connect sends access keys in the clear. chango generates a certificate for the surface so it can come up at all.

    Replacing it with your own CA's certificate

    A certificate chango generated is not something a corporate PKI will accept, and the alternative — telling every client to trust one chango made — does not scale past the first audit. So the surface's certificate can be replaced, from the gateway's Configure → TLS Certificate tab or:

    curl -sS -X POST $BASE/admin/api/trino-gateway/<clusterId>/nginx/certificate \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d "$(python3 - <<'PY'
import json
print(json.dumps({
  "certificate": open("gw.crt").read(),      # the leaf
  "privateKey":  open("gw.key").read(),
  "chain":       open("intermediate.crt").read(),   # omit if there is none
}))
PY
)"
#   {"subject":"… CN=gw.corp.example","issuer":"… CN=Corp Issuing CA",
#    "notAfter":"Jan 28 10:44:10 2029 GMT","daysRemaining":824,
#    "selfSigned":false,"chainCerts":1}

    The PEMs are read from files rather than passed as arguments on purpose — an argument lands in shell history and in ps output.

    GET …/nginx/certificate/info answers the question an operator asks before replacing anything — subject, issuer, SANs, expiry, fingerprint, and whether it is still the one chango generated. The tab renders it, with a badge when the certificate expires within 30 days.

    What the node refuses, and what each would have caused

    Validation happens on the node that will serve the certificate, before anything is written. Every one of these installs cleanly otherwise and fails later at a client, in a message that names neither the host nor the file:

    Sent Refused with Had it been allowed
    key that does not match the certificate the private key does not belong to this certificate nginx refuses to start — the surface goes down at the next reload, not at the install
    expired certificate this certificate expired on … every client fails at once while the file looks correctly installed
    no subjectAltName this certificate has no subjectAltName modern clients, Java included, do not fall back to the common name — trusting the CA cannot save it
    SAN not covering the host none of this host's names … is in the certificate's SAN same
    passphrase-protected key nginx cannot be prompted for one the surface simply never comes back after a reload

    A failed nginx -t restores the previous pair and reloads, so a bad certificate cannot take the surface down. ssl_certificate is written as leaf + intermediates in one file: serving the leaf alone works for clients that already hold the intermediate and fails for the rest, which is the worst kind of half-working.

    Confirming it — ask the port, not the screen

    openssl s_client -connect <surface>:<port> -servername <surface> \
  -CAfile corporate-root-ca.pem </dev/null 2>/dev/null \
  | grep -E "Verify return code|subject="
#   Verify return code: 0 (ok)

    The screen shows the file chango read; the port shows what clients get. The two differ when a reload failed. example/tls/verify_python.py carries this through to a query, and example/tls/java/ does the same for a JVM client, which needs its own trust store either way.

    Trusting the certificate

    curl -k skips verification. Clients that cannot — the JDBC driver, the workflow's SQL task — fail like this:

    PKIX path building failed: unable to find valid certification path to requested target

    That message reads like a wrong address or wrong credentials. It means the client has nothing to verify against.

    The short path — let chango distribute it

    The file has to be on every node the client can run on, at the same path. Copying it by hand is where it goes wrong: miss one node and only the executions that land there fail, which reads as an intermittent network problem. So ask chango to place it, from the workflow page's Trust Store tab or:

    curl -X POST $BASE/admin/api/kiok/<clusterId>/truststore \
     -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
     -d '{"gatewayClusterId":"tg-1"}'
# {"path":"/etc/chango/certs/tg-1.pem",
#  "nodes":["nm-cp-1…","nm-cp-2…","nm-cp-3…"],
#  "gatewayEndpoint":"https://cp-2.chango.private:19300",
#  "taskConfigKeys":{"trino":"trino.ssl.trustStore: /etc/chango/certs/tg-1.pem", …}}

    The certificate is read off that gateway's own TLS surface, so there is nothing to copy or paste. Pass a certificate (PEM) instead to install a corporate CA — a JVM does not know that CA either, so it fails exactly like a self-signed one, except one CA certificate covers every server certificate it issues and survives their reissue.

    The same distribution exists for the engines themselves (Trino, Trino Gateway, Spark, Flink, Ontul) and for the control plane's own calls — see Trust Store. Reading the certificate off the gateway pins the leaf it serves today; the tab says so, and a renewal means running it again.

    taskConfigKeys is the line to paste, per task type. The prefix differs (trino. / ontul. / livy. / none for http) and a wrong prefix is silently ignored — the result is a PKIX failure that says nothing about the setting.

    python and shell tasks are not covered

    Those keys configure the worker's JVM clients. A script that calls HTTPS itself uses its own runtime's trust store, so in one DAG the http task passes and the python task fails with CERTIFICATE_VERIFY_FAILED. Build the context in the script: ssl.create_default_context(cafile="/etc/chango/certs/tg-1.pem").

    The long path — a JVM-wide trust store

    For a client with no per-task setting, fetch the certificate and build a trust store:

    curl -sS $BASE/admin/api/trino-gateway/<clusterId>/nginx/certificate \
  -H "Authorization: Bearer $TOK"
#   {"endpoint":"https://<nginx host>:19300",
#    "certificate":"-----BEGIN CERTIFICATE-----…"}

    The endpoint comes back with it because there are two distinct failures — "cannot verify" and "verified, but reached by a name the certificate does not cover" — and the certificate covers the host's FQDN, its address and localhost.

    JDK=$(ls -d /opt/*jdk-17* | head -1)
sudo mkdir -p /etc/chango && sudo chmod 755 /etc/chango
sudo cp -n $JDK/lib/security/cacerts /etc/chango/truststore.jks   # copy, don't create
sudo chmod 644 /etc/chango/truststore.jks
sudo $JDK/bin/keytool -importcert -noprompt -trustcacerts \
     -alias chango-trino-gateway -file /tmp/gw.crt \
     -keystore /etc/chango/truststore.jks -storepass changeit

    Copy cacerts — never hand a JVM an empty trust store

    A fresh keystore holding only this certificate makes that JVM lose every public CA, and its other outbound HTTPS calls start failing quietly.

    Not under /opt/chango/conf

    On master nodes that directory is 750 — it holds the master key — so component accounts cannot read it. The JVM then falls back to an empty trust store and fails PKIX while the file plainly exists with a matching fingerprint. Only master nodes are affected, so it presents as an intermittent network problem:

    DAG run 1) SUCCESS  driver=worker-on-nm-only-node     ← conf is 755 there
DAG run 2) FAILED   driver=worker-on-master-node
DAG run 3) FAILED   driver=worker-on-master-node

    Keep it somewhere component accounts can read, and check as that account: sudo -n -u kiok test -r /etc/chango/truststore.jks.

    Point the consuming component's JVM at it. For the workflow engine set both roles — tasks execute on workers, and the master is on the path too:

    curl -sS -X POST $BASE/admin/api/kiok/<clusterId>/config \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' -d '{
  "masterJvm":{"extra":{
    "-Djavax.net.ssl.trustStore":"/etc/chango/truststore.jks",
    "-Djavax.net.ssl.trustStorePassword":"changeit"}},
  "workerJvm":{"extra":{
    "-Djavax.net.ssl.trustStore":"/etc/chango/truststore.jks",
    "-Djavax.net.ssl.trustStorePassword":"${TRUSTSTORE_PASSWORD}"}}}'

    Verify by running the same job several times: one success only proves the node it happened to land on. Every worker should appear as the driver.

    Re-applying nginx reuses the existing certificate, so the fingerprint is stable and trust stores stay valid — including one installed through the TLS Certificate tab.

    Rotating a certificate issued by the same CA needs no client-side work at all: that is the whole reason to trust the CA rather than the server certificate. Replacing a chango-generated one, or deleting /etc/nginx/ssl/<conf>.crt so a new one is generated, does invalidate the trust stores built from it.

    Why a missing route looks like an auth failure

    The gateway authenticates the caller first, then asks which cluster-group that identity belongs to, then routes. A user with valid credentials and no group membership fails at the second step — and the response the client sees is a 401.

    So when a freshly installed gateway rejects a correct username and password, check membership before checking the password. The kiok tutorial walks the same path with a DAG in front of it.

    Resource groups

    Optional. They cap concurrency and memory per group of queries:

    curl -sS -X POST $BASE/admin/api/gateway/resource-groups \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"name": "adhoc", "…": "…"}'

    Values are stored opaquely — chango persists whatever JSON is posted and hands it to the gateway, which owns the schema. Without a resource group the gateway applies its own defaults.

    Where the topology lives

    Under gateway.* keys in the replicated metadata store:

    Key Holds
    gateway.cluster.<name> Cluster JSON
    gateway.cgroup.<name> Cluster-group JSON
    gateway.rgroup.<name> Resource-group JSON
    gateway.usergroup.<user> The user's cluster-group name, mirrored from Ontul

    Two consequences worth knowing:

    • It is covered by the chango master backup. A restored master brings its routing back with it — see Backup & Restore.
    • It is leader-written. Mutating calls against a follower answer 421 with the leader's address rather than writing to a store that trails.

    API summary

    Method Path Notes
    GET / POST / DELETE /admin/api/gateway/clusters[/<name>] Backend Trino clusters
    GET / POST / DELETE /admin/api/gateway/cluster-groups[/<name>] Routing groups; POST also creates the Ontul group
    GET / POST / DELETE /admin/api/gateway/resource-groups[/<name>] Concurrency / memory limits
    GET /admin/api/gateway/user-groups Membership, mirrored from Ontul
    ~~POST / DELETE~~ ~~/admin/api/gateway/user-groups~~ 410 Gone — manage membership in Ontul
    GET / POST /admin/api/trino-gateway/<id>/nginx The client surface — candidates, then apply
    GET /admin/api/trino-gateway/<id>/nginx/certificate Its certificate + the endpoint it is valid for
    POST /admin/api/trino-gateway/<id>/attached-groups Which groups this gateway serves — replaces the whole list

    attached-groups replaces, it does not add

    Sending only the new group drops the others — including default, which stops operator queries. Send the full list every time.

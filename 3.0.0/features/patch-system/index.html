    Patch System

    Chango ships an air-gapped patch system for swapping a component's JAR files and / or its admin-UI bundle on a running cluster without going through the full install / configure cycle. Patches are jar / UI only — they never touch operator-edited configuration (conf/*), per-instance install metadata, RocksDB state, or component data. The control plane treats a patch as an immutable, signed-by-sha256 artifact that flows from chango-pack patch on the build host, through the operator's browser (upload), into the chango master's patch library, and out to every host that runs an instance of the target component.

    What problem it solves

    A managed component (Ontul, kiok, ShannonStore, …) has a hotfix you want to deploy across the fleet:

    • Without the patch system, the operator either re-runs the full ansible install (overwrites configuration, restages tarballs) or hand-edits lib/*.jar on every host (no audit, no rollback, easy to skew across hosts).
    • With the patch system, the operator builds a tarball once with chango-pack patch, uploads it once to the admin UI, and clicks Apply — the leader fans out per-host swap + restart with automatic backup and one-click rollback.

    Component coverage

    What is patchable is exactly what chango wrote. Everything else is an open-source artifact whose version chango picked after testing the stack against it, and swapping one of those is not a patch — it is an upgrade.

    Component What a patch may carry
    Ontul · kiok · ItdaStream · ShannonStore · NeoRunBase · Mium lib/*.jar, admin-ui/**
    chango itself lib/*.jar, admin-ui/** — see self-patch
    Trino Gateway · UI Proxy lib/*.jar — chango wrote these; they ship as components
    Trino · Spark · Flink plugin/<name>/*.jar only — the authorization plugin, never lib/

    The engines are the interesting row. chango's authorization plugin runs inside Trino, Spark and Flink, so it has to be patchable — but their lib/ holds the engine itself. So for those three the tool refuses --jars outright:

    $ chango-pack patch --component trino --type jar --jars ./build/libs --out p.tgz
chango-pack patch: 'trino' 은 --jars 를 쓸 수 없습니다 (lib/ 은
  chango 가 버전을 고정한 오픈소스 jar 입니다). chango 의 플러그인만
  --plugin <이름>=<디렉터리> 로 담으세요.

    and the upload re-checks every path in the extracted tree against the component, so a hand-assembled tarball does not get through either.

    To move an engine to a different version, use Blue / Green Upgrade.

    A plugin patch only touches hosts that have that plugin

    Where a plugin belongs is the installer's decision — the engines' authorization plugin is installed on coordinators only. A patch that created plugin/<name>/ on a worker would leave the first-party jar there without the dependencies the installer would have put beside it. Trino loads it anyway, because the plugin class itself needs nothing, so the drift stays invisible until a release touches a dependency at class-init and that worker stops starting. So an instance without the directory is skipped, and the node manager logs that it skipped it.

    The matching rule on the way back: if a rollback empties a plugin directory, the directory goes with its last jar. An empty plugin directory is worse than none — Trino refuses to start with No service providers of type io.trino.spi.Plugin in the classpath: [].

    Building a patch — chango-pack patch

    chango-pack is the air-gapped tooling shipped inside the chango release tarball. The patch sub-command builds the upload-ready tarball from a directory of jars and / or a directory of admin-UI dist files:

    # Java-only patch
/opt/chango/bin/chango-pack patch \
    --component ontul \
    --version   3.0.0-SNAPSHOT \
    --type      jar \
    --jars      /path/to/ontul/lib \
    --out       dist/ontul-patch-3.0.0-SNAPSHOT.tgz

# admin-UI-only hot patch (no restart needed)
/opt/chango/bin/chango-pack patch \
    --component kiok \
    --version   3.0.0 \
    --type      ui \
    --admin-ui  /path/to/kiok/admin-ui/dist \
    --notes     "fix DAG status colors" \
    --out       dist/kiok-patch-3.0.0-ui.tgz

# combined jar + UI
/opt/chango/bin/chango-pack patch \
    --component shannonstore \
    --version   3.0.0 \
    --type      both \
    --jars      /path/to/shannonstore/lib \
    --admin-ui  /path/to/shannonstore/admin-ui/dist \
    --out       dist/shannonstore-patch-3.0.0.tgz

    The output is a tgz whose layout is strictly:

    manifest.json              ← {component, version, type, files[].sha256, builtAt, builtBy, ...}
lib/*.jar                  ← required when --type is jar or both
admin-ui/dist/**           ← required when --type is ui  or both

    Any other top-level entry, or any path outside this whitelist, is rejected at upload time. No conf/, no scripts, no full install tree.

    The tooling only needs tar, sha256sum, find, and a POSIX shell — it ships inside /opt/chango/bin/ so the same chango release can rebuild patches in-place on the build host.

    REST surface

    Endpoint Purpose
    POST /admin/api/patch/upload Raw tarball (Content-Type: application/gzip) → leader validates whitelist + sha256, stores under data/master/patches/.
    GET /admin/api/patch/library Lists every uploaded patch. Optional ?component=ontul filter.
    GET /admin/api/patch/<patchId>/raw Authenticated download of the original tarball (used by node managers when the master orchestrates an apply).
    POST /admin/api/patch/<patchId>/apply Body {clusterId, restartMode: "rolling"|"parallel"} — fans out per-host swap + restart.
    POST /admin/api/patch/rollback Body {component, clusterId, to: "lastBackup"|patchId} — restores lib/ and admin-ui/ from .bak/.
    GET /admin/api/patch/history?component=&clusterId= Per-cluster applied-patch history (read-only fan-out to each NM's .bak/* dirs).

    All mutating routes are admin-only (Stage-1 RBAC) and leader-only. Followers transparently forward to the leader.

    Every /admin/api/patch/* route runs on the admin worker pool (chango.master.admin.worker.threads), not on the HTTP event loop. An upload writes a 10 MB+ tarball and a chango self-patch waits minutes for the follower masters; on the event loop that blocked every other connection assigned to the same loop, so catalog listings on a leader that was up the whole time timed out during a patch. A self-patch holds one worker thread while it waits.

    A component patch whose target node manager is not registered reports that host as nm-not-found with the reason, rather than a bare status that reads like a mistyped node id.

    Upload

    TOK=$(curl -s $BASE/admin/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<pw>"}' | jq -r .accessToken)

curl -X POST -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/gzip' \
     --data-binary @dist/ontul-patch-3.0.0-SNAPSHOT.tgz \
     $BASE/admin/api/patch/upload

    Response:

    {
  "patchId":   "ontul-3.0.0-SNAPSHOT-20260530-1f3a",
  "component": "ontul",
  "version":   "3.0.0-SNAPSHOT",
  "type":      "jar",
  "size":      18234567,
  "sha256":    "…",
  "uploadedAt":"2026-05-30T12:34:56Z"
}

    Apply

    curl -X POST -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/json' \
     -d '{"clusterId":"ontul-main","restartMode":"rolling"}' \
     $BASE/admin/api/patch/ontul-3.0.0-SNAPSHOT-20260530-1f3a/apply

    The leader resolves (component, clusterId) to the set of NMs that host an instance, then sends each NM a PATCH_APPLY (OpCode 235) carrying the manifest + a master-side /raw download URL + the explicit instanceIds to swap on that host (the NM has no clusterId/role context of its own). The NM:

    1. Downloads the tarball from the master via the authenticated /raw route.
    2. Backs up the current lib/ (and admin-ui/dist/ if type == ui|both) of every targeted instance into <install-dir>/.bak/<patchId>/ — unconditional, every apply.
    3. Overlays the patch contents on top of the live install dir — lib/*.jar replaces matching jars, admin-ui/dist/** overlays the bundle. No file outside the whitelist is touched.
    4. Restarts the instance with the component's existing bin/stop-*.sh + bin/start-*.sh (only when type == jar|both — a UI-only patch needs no restart). JAVA_HOME and the original -Dchango.* system properties are preserved from the live pid's /proc/<pid>/cmdline.

    restartMode: "rolling" does this one host at a time and waits for the instance to report RUNNING again before moving on; parallel fires every host together — faster, but expects all instances to tolerate a simultaneous restart.

    The response aggregates per-host results:

    {
  "patchId":   "ontul-3.0.0-SNAPSHOT-20260530-1f3a",
  "clusterId": "ontul-main",
  "status":    "applied",
  "hosts": [
    {"nodeId":"nm-host1-…", "instanceIds":["ontul-main-master"],  "status":"applied"},
    {"nodeId":"nm-host2-…", "instanceIds":["ontul-main-worker-1"],"status":"applied"},
    {"nodeId":"nm-host3-…", "instanceIds":["ontul-main-worker-2"],"status":"applied"}
  ]
}

    Rollback

    curl -X POST -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/json' \
     -d '{"component":"ontul","clusterId":"ontul-main","to":"lastBackup"}' \
     $BASE/admin/api/patch/rollback

    Rollback is the inverse of apply: each NM restores lib/ and admin-ui/dist/ from the requested .bak/<patchId>/ directory and restarts the instance. to: "lastBackup" rolls back to the most recent apply; to: "<patchId>" rolls back to a specific past patch. Rollback also writes a fresh .bak/<rollbackId>/ so a re-roll-forward stays possible.

    Because .bak/ lives inside the instance install dir, rollback only sees patches that were applied to that host — not the master's global library. If you wiped /opt/components/<instanceId>/.bak/ by hand, the corresponding rollback target is gone.

    History

    curl -s -H "Authorization: Bearer $TOK" \
     "$BASE/admin/api/patch/history?component=ontul&clusterId=ontul-main" | jq .

    Returns the list of patches whose .bak/ is still present on the cluster — applied in newest-first order, one row per (patchId, host). The admin UI uses this to drive the PatchHistoryCard on each component page.

    For component=chango the rows have the same shape as for a component — {patchId, instanceId, nodeId, createdAt} plus version, type, notes, builtAt, uploadedAt — with instanceId set to chango control plane and one row per host the patch reached. Those come from appliedPatchMeta, a record of {appliedAt, hosts[]} per patch kept next to the apply order. A patch applied before that record existed shows a single row with no host and no time, and the console prints — there rather than Invalid Date or 1970. Rolling a patch back drops its record too.

    On-disk layout

    <install_dir>/data/master/patches/
    <patchId>.tgz                ← the raw uploaded tarball
    <patchId>.json               ← parsed manifest + sha256

/opt/components/<instanceId>/
    lib/                         ← live jars  (overlaid by patch apply)
    admin-ui/dist/               ← live UI    (overlaid by patch apply)
    .bak/
        <patchId>/
            lib.tgz              ← pre-apply backup
            admin-ui.tgz         ← pre-apply backup (when applicable)
            manifest.json        ← copy of the applied manifest

    The leader keeps the master library; each NM keeps the per-instance backups. Two different chango clusters never share a .bak/.

    Non-leader catch-up (PR 5)

    Followers and node managers must not call out to the leader's HTTP API on every PATCH_APPLY — that would couple every NM's apply path to the leader's admin port. Instead, the patch library is treated like any other chango cluster state: replicated lazily over the internal NIO protocol.

    • OpCode PATCH_INDEX_REQ / PATCH_INDEX_RES — leader returns a JSON array of every patchId + sha256 currently in its library.
    • OpCode PATCH_FETCH_REQ / PATCH_FETCH_RES — body is the patchId as UTF-8; leader streams the tarball back.

    A non-leader master runs PeriodicLeaderPull every 30 s: pull the index, compare with the local patches/ dir, fetch any missing tarballs. The same pull runs immediately when this master loses leadership so a brand-new follower never serves a stale library.

    This is also what makes the patch system survive a backup / restore: when a fresh chango cluster restores from a backup tarball, the leader's data/master/patches/ directory is included (see below), and every newly-elected follower pulls from it on startup.

    Backup inclusion

    BackupService.packTarball includes data/master/patches/ in the cluster-state backup whenever the directory exists. The manifest reflects this:

    {
  "backupId":       "20260530-…",
  "patchesDir":     "/opt/chango/data/master/patches",
  "patchesIncluded": true,
  ...
}

    Restoring the backup re-populates the patch library on the new master; followers then catch up via PATCH_INDEX / PATCH_FETCH.

    Admin UI

    Settings → Patches

    Sidebar → Settings → Patches opens the cluster-wide patch console:

    • Upload — drag-and-drop dropzone. POSTs the raw .tgz body to /admin/api/patch/upload with the operator's bearer token. On success the new patch shows up at the top of the Library.
    • Library — every uploaded patch, newest first, grouped by component. Each row shows version, type, size, sha256 (truncated, click to copy), uploadedAt, notes, and an Apply button that opens the Apply modal.
    • Apply modal — pick a cluster (autopopulated from the existing instances of the patch's component), pick rolling or parallel, confirm. The modal streams the leader's response and surfaces per-host status as it lands. Above the restart choice it shows the selected cluster's installed version and patch level, with every recorded patch id, and warns when this patch would be a downgrade or crosses a major version.

    Patch History card on each component page

    Every component's detail page (Ontul, kiok, ShannonStore, NeoRunBase, ItdaStream, Mium) shows a PatchHistoryCard in the right-hand panel listing the patches applied to the current cluster — one row per patch with Rollback to last backup (header) and Rollback to this (per row).

    Both rollback buttons open a confirmation, Roll back patch, that names the target cluster and which backup it restores and says it cannot be undone from there; the confirm button reads Roll back. For chango itself the target is every master and node manager. They used to run on a single click.

    Non-admin readonly

    Non-admin users (members of any group that does not hold the AdministratorAccess policy) see the Patches page in read-only mode — the Library is visible, but Upload, Apply, Rollback buttons are hidden, and the dropzone is disabled. The backend enforces the same gate.

    Patch level, and what a scale-out does with it

    A patch does not change the cluster's version. That field names the component package the cluster was installed from — ontul/ontul-1.0.0.tar.gz — and a patch replaces jars inside an install without touching the package on the master. The two facts are reported separately:

    GET /admin/api/patch/level?clusterId=<id>
→ { "clusterId": "...", "patchLevel": "1.0.1",
    "appliedPatches": [ { "patchId": "ontul-1.0.1-ab12cd34ef56", "version": "1.0.1", "type": "jar" } ] }

    The Apply drawer shows both, because the difference is the thing an operator has to understand before clicking: installed version is what a scale-out or a reinstall installs from, patch level is what is running now.

    A scale-out replays the cluster's patches

    Applying a patch records its id on the cluster. When a scale-out adds instances, the patches recorded for that cluster are replayed onto the new instances before the call returns — in the order they were applied, since a later patch may overwrite a file an earlier one also carried.

    Without that, a scale-out installed the new instance from the cluster's stored packageFile and nothing else: it came up running pre-patch code while every one of its peers ran the patch. Nothing reported an error, the Patches page showed the patch as applied, and the divergence surfaced only once work happened to land on the new instance.

    The replay does not start anything

    A jar patch normally restarts the instance it lands on, because the JVM has the old jars open. A scale-out instance has not been started yet, so a restart there would be a start — and chango keeps install and start separate everywhere else. The node manager therefore restarts only instances that are actually up and simply swaps the jars of the rest; a stopped instance picks them up whenever it is started. The ack reports both what the manifest demanded (restarted) and what happened (restartedInstances).

    Rollback un-records it. Otherwise the next scale-out would replay the patch the operator just removed, and the new instance would be the only one carrying it — the original bug, reversed.

    A reinstall does not replay. The record lives in the cluster's own settings, so deleting the cluster drops it. That is deliberate: a reinstall is a fresh install from the component package, and silently re-applying patches to what the operator asked to be new would be a different product than the one they asked for. Re-apply from the Library afterwards — the tarball never GCs, so it is still there.

    A patch deleted from the library cannot be replayed

    If a recorded patch is no longer in the library, the scale-out logs it and the new instances stay at the package level. appliedPatches marks that entry "missing": true rather than hiding it: the cluster claims a level it can no longer reproduce, and only the operator can resolve that.

    Versions are reported, not enforced

    Nothing refuses a patch whose version does not match the cluster's. Applying an ontul 1.0.1 patch to a 1.0.0 cluster is the ordinary case; applying 0.9.5 to it is a downgrade, and applying a 2.x patch to a 1.x cluster will not migrate state or config for you. The Apply drawer says so for the last two and then lets you proceed — an operator rolling back to a known-good build at 3am is doing something legitimate, and a hard refusal there is worse than a warning.

    Invariants

    The patch system is deliberately narrower than "in-place upgrade":

    • Configuration is never touched. The whitelist excludes conf/. Operator-edited properties files survive every apply / rollback.
    • State is never touched. data/, logs/, RocksDB stores under the component's install dir are untouched. Iceberg files, Kafka logs, NeoRunBase tables are unaffected.
    • Backups are unconditional. Every apply writes a fresh .bak/<patchId>/ before overlaying anything. The operator does not have to opt in.
    • Patches are immutable. patchId is a content-derived id; the same tarball uploaded twice deduplicates.
    • A scale-out stays level with the cluster. Patches recorded on a cluster are replayed onto instances a scale-out adds. A reinstall is not — see Patch level.
    • The version field keeps meaning "which package". A patch never rewrites it, because a scale-out and a reinstall both resolve their package from it.
    • Only what chango wrote. Open-source jars are never patched — chango pins their versions after testing the stack against them. For the engines that means the authorization plugin and nothing else.
    • Every patch carries an SBOM and a checksum. A patch enters an air-gapped site the same way a bundle does, so it is held to the same standard: <out>.sha256 beside the tarball to check after the transfer, and sbom/<component>-<version>-patch.cdx.json inside it listing what the patch ships (not the whole install).
    • A restarted instance is watched. start() returns when the launcher returns, which is before the process has decided whether it can run. Apply and rollback wait to see the instance stay up and fail that instance otherwise, so one that dies on startup triggers the per-instance rollback instead of being reported as a success.

    Chango self-patch

    The patch system also patches chango itself — the chango JARs and the chango admin UI. The contract is identical:

    /opt/chango/bin/chango-pack patch \
    --component chango \
    --version   3.0.0 \
    --type      both \
    --jars      /path/to/chango/lib \
    --admin-ui  /path/to/chango/admin-ui/dist \
    --out       dist/chango-patch-3.0.0.tgz

    A chango patch has to carry four modules together — chango-common, chango-cluster, chango-protocol, chango-master — and chango-pack refuses one that is missing any of them. They call each other directly, so shipping one without another produces an install that passes the build, passes the upload, reports all hosts ok, and then will not start:

    Exception in thread "main" java.lang.NoSuchMethodError:
  'long com.cloudcheflabs.chango.common.config.ChangoConfig.getNginxCertInstallTimeoutMs()'

    That is a real one: a config accessor added to chango-common, a patch built with only chango-master and chango-node-manager, and three masters down while the patch system said every host was fine. Carrying an unchanged module costs a few hundred KB. Omitting one costs the control plane.

    What differs is the execution model — chango is patching itself, so it can not be the process that overlays its own running JARs. Apply runs a 3-phase fan-out through a detached helper:

    1. Node managers first.
    2. Follower masters next.
    3. Leader self last.

    On every target host the master forks a setsid-detached helper that does sleep 3 && download && backup .bak/<patchId>/{lib,admin-ui}.tgz && overlay && stop-master.sh / stop-node-manager.sh && start-…sh. The helper carries every CHANGO_* variable and JAVA_HOME of the running process, plus its original -Dchango.* system properties from /proc/<pid>/cmdline, and passes the list as CHANGO_CARRY_ENV so the start script re-exports the same set across the sudo -u chango boundary. It used to carry only CHANGO_MASTER_KEY and JAVA_HOME; a node manager started with CHANGO_ZK_SERVERLIST then came back with chango.zk.serverList is not configured and exited, while the patch reported the host as patched.

    What restarts, and in what order

    Patch type What the helper does
    ui Overlays admin-ui/ and stops nothing. The master reads the admin UI from disk on every request, so the new bundle is served as soon as the files are written.
    jar, both Overlay, then stop and start the role on that host.

    For jar / both the fan-out is:

    1. Node managers, all of them. The helper waits up to 60 s for the node manager's pid file and process to be back before it writes DONE; if it is not back, the helper fails (.self-patch-failed, exit 1) and says the jars are in place but the service is down, with the previous install under .bak/<patchId>/.
    2. Follower masters, one at a time. After sending to a follower the leader waits until that follower has re-registered in ZooKeeper (a new registration znode, not the old one still standing) and reports ready, up to chango.master.selfpatch.follower.wait.ms (default 180000, in conf/chango.properties). A follower on a host that also runs a node manager queues behind that node manager's helper on the host lock, so the wait has to cover both restarts. It used to be a fixed 8 s, which on such a host ran out before the follower had even stopped — and the leader then restarted in the same second, leaving no master to answer.
    3. The leader, last.

    If a follower does not come back within the wait, the leader is not restarted — restarting it too would leave no master. It keeps the previous version and the response says so:

    {
  "patchId": "chango-3.0.0-…",
  "component": "chango",
  "status": "self-patch-leader-held",
  "restarts": true,
  "hosts": [
    {"nodeId": "nm-host1-…", "role": "nm",          "status": "ack"},
    {"nodeId": "nm-host2-…", "role": "nm",          "status": "ack"},
    {"nodeId": "master-host2-…", "role": "follower", "status": "ack"},
    {"nodeId": "master-host1-…", "role": "leader-self", "status": "held",
     "error": "follower master master-host2-… did not come back within 180s, so this leader was not restarted — restarting it too would leave no master. It keeps the previous version. Check that follower's self-patch log, then apply again."}
  ]
}

    A normal run answers "status": "self-patch-scheduled". Per-host statuses are ack, failed, transport-error, held, and unreachable — the last for a host that carries component instances but is not in the node registry (its ZooKeeper session is gone). That row says how many instances on it keep the previous version: restart its node manager and apply again. Before, such a host was simply absent from the list and the result looked complete.

    While the leader restarts itself there is a window of a few seconds in which leadership moves and admin API calls can be refused; the sticky-leader hint (below) brings leadership back to the same node.

    The leader's own step is started inside the leader process, not sent to itself over the internal protocol. That request used to time out on the leader's own port: the helper never ran, the leader stayed on the old jars, and — because a node manager on the same host had already overlaid the shared lib/ — the jar checksums still matched the patch. Judge a self-patch by each host's self-patch-<patchId>.log (a DONE line for every role on that host, role=master included on the leader host) and by the master process start time, not by jar checksums.

    The Patches screen survives its own master restarting. When the master serving the screen restarts mid-apply, the browser loses the connection; the screen then shows Control plane restarting — confirming the result… and reads /admin/api/patch/level and the patch history until a record newer than the click appears (up to five minutes), instead of reporting a network error for a patch that went through. Applying the same patch again is confirmed the same way.

    A fix to the orchestration itself takes effect from the next patch

    The fan-out and the helper script are run by the code that is already running when you click Apply. A patch that changes how self-patching works — the order, the wait, what the helper carries — is delivered by the old orchestration, and its own behaviour first shows on the patch after it.

    On a host that runs both a master and a node manager the helper runs twice, once per role, serialised by a host lock. The tarball is downloaded once per host: the first role caches it under /opt/chango/.patch-cache/<patchId>.tgz and the second re-checks it with gzip -t and uses it, so it does not depend on the master that serves /raw still being up. When a download is needed it is retried for longer than one leader restart (curl --retry 10 --retry-delay 3 --retry-all-errors --retry-connrefused; without --retry-all-errors curl does not retry exit 18, a truncated transfer). Before this, the node manager's restart on a shared host overlapped the leader's own restart, the master role's download was cut off, and that master went on serving pre-patch code while the apply said ack.

    The download is retried, size-checked and gzip -t'd before anything is stopped, and the helper's fail() is defined before the first thing that calls it. All three exist because of one incident: the leader was being restarted as part of the same rolling sequence a follower was downloading from, curl exited 18 on the truncated transfer, and fail was declared further down the script — so the shell printed fail: command not found, carried on, stopped the master, overlaid a half-extracted stage directory, started it again and wrote DONE. The failure marker was never written either; writing it is what fail() does.

    set -e is deliberately not used instead. The helper relies on non-zero exits in several places — looking for a backup, probing for nginx — and would abort on the first of them.

    Because the leader writes a master-leader-preferred:<expiresAt> hint to ZooKeeper just before its graceful stop, the sticky-leader mechanism (see Sticky Leader Election) reclaims leadership for the same nodeId once the helper finishes the restart — no leadership toggle, no double KMS / IAM init.

    Rolling a self-patch back

    curl -X POST -H "Authorization: Bearer $TOK" \
     -H 'Content-Type: application/json' \
     -d '{"component":"chango","clusterId":"chango","to":"lastBackup"}' \
     $BASE/admin/api/patch/rollback

    Same route as any other rollback, and the same 3-phase fan-out in the same order — node managers, then follower masters one at a time so quorum survives, then the leader last. The recorded level is cleared before the leader restarts itself; a write deferred past that point would never run.

    The route dispatches on the component because chango has no component instances: its jars live in /opt/chango, not under /opt/components. The generic instance-based path would find nothing and answer no-instances, which reads like "nothing to do".

    to: "lastBackup" means each host's own newest snapshot, and the response says so. That matters when hosts are not level — a rollback restores each host to what that host was running, which is the correct behaviour and not necessarily one uniform build.

    The snapshot is a full directory tarball (lib.tgz, admin-ui.tgz), not a patch-sized diff, so a restore is an extract and cannot leave a half-reverted install.

    One backup per host, not per role

    A host that runs both a master and a node manager runs the helper twice, once per role, against the same /opt/chango. Both used to take a backup — so the second captured the state the first had already overlaid, and .bak/<patchId>/lib.tgz ended up holding the patched jars. A rollback then restored the patch and logged restore lib … DONE. On a 3-node cluster the two colocated nodes silently kept the new code while the third went back, leaving the control plane running two different builds.

    The backup is now taken once per host per patch: whichever role takes the host lock first captures the pre-patch state, and the second keeps it. If you are reading this because you are auditing an older install, compare .bak/<patchId>/lib.tgz's contents against the running jars before trusting a rollback.

    Verifying a self-patch

    The helper is detached, so the RPC answers helper-spawned before anything has been swapped. That ack is not evidence. Check four things:

    1. the jar's checksum on every host matches the one you built,
    2. the process actually restarted (ps -o lstart=),
    3. the level record lists the patch (GET /admin/api/patch/level?component=chango&clusterId=chango),
    4. the behaviour you patched actually changed.

    A helper that fails after the ack leaves /opt/chango/.self-patch-failed and a log under <chango log dir>/self-patch-<patchId>.log — read those before concluding a patch "did nothing". The master also reads the marker on every start and logs it at ERROR — A self-patch failed on this host and was never applied. This process may be running code older than the jars on disk … — until a later successful patch of that role removes it. Re-apply from Settings → Patches, or roll back; the previous install is under /opt/chango/.bak/<patchId>.

    For a ui patch, check (1) and (4) only: nothing restarts.
